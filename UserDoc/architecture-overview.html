🔭 Project Overview

Eclipse SysON is an open-source, web-based SysML v2 modeling tool built on the Eclipse Sirius Web platform. It provides graphical, form-based, and tabular editors that allow engineers to create, modify, and visualize system models conforming to the OMG SysML v2 standard.

SysON is developed jointly by Obeo (product and UX focus) and CEA (SysML v2 compliance and OMG representation). It is the core of the SysML v2 editing feature in Papyrus and supports co-design with Eclipse Capella.

🗂 Architectural Layers

SysON follows a layered architecture where each layer has a clearly defined responsibility and dependency direction — inner layers have no knowledge of outer layers.

🖥 Browser UI React components, Sirius Web widgets, GraphQL subscriptions
📡 GraphQL API Spring GraphQL — queries, mutations, subscriptions; REST API (SysML v2 standard)
🧩 View / Representation Layer Sirius Web view descriptions — diagram nodes, edges, tables, trees, forms
⚙ Service Layer Business logic organized by concern (diagram, table, tree, form, model)
🔷 SysML v2 Metamodel EMF-based model objects — no Spring, no Sirius dependencies

Data flows from the browser via GraphQL into the Spring handler layer, which delegates to view descriptions and service classes. Services that mutate the model ultimately operate on EMF model objects persisted through Sirius Web's storage layer into PostgreSQL.

Communication with Backend

The frontend communicates exclusively via GraphQL — there are no direct REST calls for model data. Subscriptions (WebSocket) are used for real-time diagram and representation updates. The SysML v2 standard REST API is a backend-only concern exposed for external tool integration.

⚙ Backend Module Structure

The backend is a Maven multi-module project. Modules are grouped into five top-level directories under backend/:

application/

Spring Boot entry point (syson-application), configuration, static frontend resource serving, and application-level wiring.

metamodel/

EMF-based SysML v2 metamodel (syson-sysml-metamodel) and its generated edit support. This is the innermost layer — no Spring or Sirius deps.

services/

All business logic, strictly organized by concern. See the Service Layer section for the full breakdown.

views/

Sirius Web view description providers — Java code that programmatically defines diagram nodes, edges, compartments, tables, and trees.

tests/

Centralized backend test modules with shared fixtures and integration test support.

releng/

Release engineering: JaCoCo aggregate coverage module (syson-test-coverage), resource indexing, and license management.

🔧 Service Layer Organization

Following ADR-002, services are organized by their concern and their allowed dependency set. This prevents framework concerns from leaking into the core metamodel and makes it easy to find where a given operation should live.

Module Responsibility Spring / Sirius Web allowed?
syson-sysml-metamodel-services Pure model query & mutation — EMF operations only (Usage, Definition categories) ✗ No
syson-model-services Model operations through Sirius Web (Create, Delete, Move, DragAndDrop) ✓ Yes
syson-diagram-services Diagram-specific query & mutation (GeneralView, InterconnectionView, labels, direct edit) ✓ Yes
syson-table-services Table-specific query & mutation (rows, columns, cells — RequirementsView) ✓ Yes
syson-tree-services Tree-specific query & mutation ✓ Yes
syson-form-services Form-specific query & mutation (widget values, validation) ✓ Yes
syson-representation-services Cross-cutting services shared across all representation types ✓ Yes
syson-sysml-rest-api-services OMG SysML v2 standard REST API implementation ✓ Yes
syson-direct-edit-grammar ANTLR grammar and parser for direct-edit expressions ✓ Yes

Class Naming Conventions

Service classes within each module follow a strict naming pattern that encodes both the representation type and the operation direction:

XXXQueryService
Read-only operations on representation type XXX
XXXMutationService
Write operations on representation type XXX
XXXQueryYYYService
Read operations focused on a specific sub-concern (e.g. DiagramQueryLabelService)
XXXMutationYYYService
Write operations on a specific sub-concern
XXXQueryAQLService
AQL entry point only. Delegates to Query services — contains no logic of its own
XXXMutationAQLService
AQL entry point only. Delegates to Mutation services — contains no logic of its own

Each module exposes exactly two AQL-facing classes (*QueryAQLService and *MutationAQLService). These are the only classes that AQL expressions in view descriptions are allowed to call. All other service classes are called from Java code only.

🌐 OMG SysML v2 Standard REST APIs

SysON implements the OMG SysML v2 standard REST API for interoperability with other MBSE tools (Papyrus, Capella, third-party clients). The implementation lives in syson-sysml-rest-api-services and follows a delegate pattern: SysON provides Spring beans that implement Sirius Web delegate interfaces; Sirius Web owns the actual @RestController classes and routing.

All endpoints are rooted at /api/rest/projects/{projectId}. Standard library elements and implied relationships are automatically excluded from all responses. Endpoints are marked @Hidden in OpenAPI — they are not shown in Swagger UI.

GET /api/rest/projects/{projectId}/commits/{commitId}/elements/{elementId} Single element by ID. Returns a JSON object with @id and @type fields plus all attributes.
GET /api/rest/projects/{projectId}/commits/{commitId}/elements/{elementId}/relationships Relationships for an element. Supports direction query param: IN, OUT, or BOTH.
GET /api/rest/projects/{projectId}/commits/{commitId}/roots Root namespace elements only (excludes standard library resources).

Custom JSON Serialization

All element responses are processed by SysMLv2JsonSerializer (a custom Jackson serializer registered via SysMLv2SerializerConfig, a Spring @ControllerAdvice). It intercepts responses from the Sirius Web object controller package and enforces the following output format:

@id fieldUnique element ID added to every serialized element
@type fieldElement class name (e.g. PartUsage, BlockDefinition)
Alphabetical attributesAll element attributes serialized in alphabetical order for deterministic output
Lowercase enumsEnum literals serialized as lowercase strings per OMG spec
Reference-only relationshipsRelated elements serialized as { "@id": "..." } references, not full nested objects
Standard library filteredElements from standard library resources are excluded from all responses
Integration tests: All endpoints are covered by Spring integration tests in ObjectRestControllerIntegrationTests and ProjectDataVersioningRestControllerIntegrationTests under backend/application/syson-application/src/test/. No OpenAPI (@Operation / @Schema) annotations are present — the endpoints are marked @Hidden and excluded from the Swagger UI.

🏗 Build Pipeline

The project uses a two-phase build. The frontend must be compiled first and its output copied into the backend's static resource directory before the Maven build runs.

Full Local Build Sequence

# 1 — Frontend: install dependencies and build all packages
npm ci && npm run build

# 2 — Copy frontend artifacts into Spring Boot static resources
cp -R frontend/syson/dist/* \
      backend/application/syson-frontend/src/main/resources/static/

# 3 — Backend: build, run all tests, generate coverage
mvn -U -B -e clean verify

# 4 — Verify coverage gates
jshell scripts/check-coverage.jsh

Useful Individual Commands

# Frontend — start dev server with live reload
npm run start

# Backend — skip tests (fast artifact build)
mvn clean verify -DskipTests

# Backend — test a single module
mvn -pl backend/services/syson-diagram-services -am test

# Backend — run one specific test class
mvn -pl backend/services/syson-diagram-services \
    -Dtest=MyTestClass test

# Frontend — run unit tests once
cd frontend/syson && npx vitest --run --config vite.config.js

CI/CD Flow (GitHub Actions)

1.Build frontend (npm ci → npm run build) + dependency health check

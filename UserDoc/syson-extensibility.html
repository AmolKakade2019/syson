Eclipse SysON — Extending SysML v2 Features

A developer guide explaining how the SysON codebase is structured for extension, what is already in place, and what effort is required to implement each missing SysML v2 diagram type and language feature.

SysON 2026.1.6  ·  Java 17  ·  Spring Boot 3.5

Can SysON Be Extended?

Short answer: Yes. The codebase is explicitly designed for extension. Every diagram type, node shape, and relationship arrow is a standalone Spring @Service bean. Adding a new one requires implementing one interface and writing ~150–300 lines of Java — no framework surgery, no OSGi plugin descriptors, no frontend changes.

The Key Insight — Gap Is in Visualization Only

The SysML v2 EMF metamodel (backend/metamodel/syson-sysml-metamodel/) is fully generated from the OMG specification and contains all 184+ element types including StateUsage, TransitionUsage, CalculationUsage, SuccessionFlowConnectionUsage, and every other type defined in the spec. These types can already be stored in PostgreSQL.

What is missing is the diagram visualization layer — the Java classes that tell Sirius Web how to draw these elements as nodes and edges on a canvas. No data model work is required.

Extension Architecture

SysON uses a layered registration model. Every representable element passes through three independent layers, each of which can be extended independently.

Layer 1 — Diagram Registration

A diagram type (e.g., "State Transition View") is registered by implementing IViewDescriptionProvider and annotating the class with Spring's @Service. SysONViewDescriptionProvider collects all such beans via constructor injection and passes their descriptions to Sirius Web. 

@Service
public class StateTransitionViewDiagramDescriptionProvider
        implements IViewDescriptionProvider {

    @Override
    public String getViewId() {
        return "StateTransitionView";
    }

    @Override
    public IRepresentationDescriptionProvider getRepresentationDescriptionProvider() {
        return new StateTransitionViewDiagramDescriptionBuilder();
    }
}
File: backend/views/syson-standard-diagrams-view/
Layer 2 — Node & Edge Providers

Inside the diagram description builder, node and edge providers define what can appear on the canvas. Each provider is a focused class responsible for one element type. They extend abstract base classes from syson-diagram-common-view. 

// Node provider for StateUsage elements
public class StateUsageNodeDescriptionProvider
        extends AbstractNodeDescriptionProvider {

    @Override
    protected String getSemanticCandidatesExpression() {
        return "aql:self.ownedMember->filter(sysml::StateUsage)";
    }

    @Override
    protected List<NodeDescription> getReusedChildren() {
        // compartments: entry/do/exit actions
    }
}
Base: backend/views/syson-diagram-common-view/.../nodes/AbstractNodeDescriptionProvider.java
Layer 3 — AQL Service Methods

AQL expressions in node/edge descriptions can call Java service methods for complex logic (label computation, visibility conditions, creation actions). These are exposed through the two designated AQL service classes per module:

  • DiagramQueryAQLService — read-only AQL helpers (label text, candidate filtering)
  • DiagramMutationAQLService — write AQL helpers (element creation, deletion)
Rule: Only these two classes are called from AQL expressions. All other service classes are called from Java code only. This keeps AQL expressions simple and avoids tight coupling between the diagram DSL and business logic.

Implementing a New Node Provider

The following pattern is used by all 40+ existing node providers. Extending AbstractNodeDescriptionProvider means only domain-specific methods need to be overridden. 

public class StateUsageNodeDescriptionProvider
        extends AbstractDefinitionNodeDescriptionProvider {

    // 1. Which elements does this node represent?
    @Override
    protected String getSemanticCandidatesExpression(String domainType) {
        return "aql:self.ownedMember->filter(sysml::StateUsage)";
    }

    // 2. What compartments appear inside the node?
    @Override
    protected List<NodeDescription> getReusedChildren(IViewDiagramElementFinder cache) {
        var children = new ArrayList<>();
        cache.getNodeDescription("StateUsage_EntryCompartment")
             .ifPresent(children::add);
        cache.getNodeDescription("StateUsage_DoCompartment")
             .ifPresent(children::add);
        cache.getNodeDescription("StateUsage_ExitCompartment")
             .ifPresent(children::add);
        return children;
    }

    // 3. Which ports (border nodes) appear on the node boundary?
    @Override
    protected List<NodeDescription> getReusedBorderNodes(IViewDiagramElementFinder cache) {
        return List.of(); // states have no ports
    }

    // 4. What tools appear in the palette when this node is selected?
    @Override
    protected List<NodeToolSection> getToolSections(...) {
        return new STVNodeToolSectionSwitch().doSwitch(element);
    }
}

Implementing a New Edge Provider

Edge providers are even simpler — typically 40–60 lines. AbstractEdgeDescriptionProvider provides the create() and link() methods; subclasses only declare source and target node types. 

public class TransitionUsageEdgeDescriptionProvider
        extends AbstractEdgeDescriptionProvider {

    @Override
    protected String getName() {
        return "STV_TransitionUsage";
    }

    // Source nodes: any StateUsage node
    @Override
    protected List<NodeDescription> getSourceNodes(IViewDiagramElementFinder cache) {
        var result = new ArrayList<>();
        cache.getNodeDescription("StateUsageNodeDescription").ifPresent(result::add);
        return result;
    }

    // Target nodes: any StateUsage node
    @Override
    protected List<NodeDescription> getTargetNodes(IViewDiagramElementFinder cache) {
        return getSourceNodes(cache); // transitions are between states
    }
}

AQL Service Convention

Important naming rule: Each service module may have exactly two AQL-callable service classes: XXXQueryAQLService (read-only) and XXXMutationAQLService (write operations). These are the only classes invoked from AQL expressions in view descriptions. All other service classes are called from Java only. 
// Called from an AQL expression in a node description:
// "aql:self.stv_getTransitionLabel()"
@Service
public class STVQueryAQLService {

    private final STVQueryService queryService;

    public String stv_getTransitionLabel(TransitionUsage transition) {
        return queryService.buildLabel(transition); // delegates; no logic here
    }
}

REST API Write Operations

SysML v2 OMG REST API — POST / DELETE support
Currently returns HTTP 405 for all write operations
High effort

SysON's internal write path goes through GraphQL mutations and Sirius Web's collaborative editing stack. Bridging this to the OMG REST commit model (which sends JSON-LD element trees in a single POST) would require a translation layer that converts OMG commit payloads into Sirius Web editing context operations.

  • REST write requests must be translated into EMF change operations on a live editing context
  • The OMG REST API uses a commit/branch versioning model that SysON does not implement (single-commit-per-project constraint)
  • Resolving cross-references in JSON-LD payloads to EMF URIs requires careful mapping
8 – 14 weeks

Implementing the State Transition View — Step-by-Step

The State Transition View is the best first extension target: the stub is already registered, the metamodel types are complete, and the pattern is identical to the General View. This walkthrough shows the exact sequence of steps.

Prerequisites: Java 17, Maven, a running SysON instance (PostgreSQL + Spring Boot). Familiarity with the General View node providers is helpful but not required.

Phase 1 — Set up the module structure

  1. Open backend/views/syson-standard-diagrams-view/. This is where AFV and STV stubs live. You will add new classes here — no new Maven module is needed for STV.
  2. Create a sub-package org.eclipse.syson.standard.diagrams.view.stv inside src/main/java/. This will hold all STV-specific providers, keeping them separate from SDV and AFV classes.
  3. Create an STVDescriptionBuilder class (implements IRepresentationDescriptionProvider). This is the wiring class that assembles node and edge providers into a complete diagram description. Copy the structure from SDVDiagramDescriptionBuilder.

Phase 2 — Create node providers

  1. Create StateUsageNodeDescriptionProvider extending AbstractDefinitionNodeDescriptionProvider. Override getSemanticCandidatesExpression() to return "aql:self.ownedMember->filter(sysml::StateUsage)".
  2. Create StateDefinitionNodeDescriptionProvider with the same pattern, targeting sysml::StateDefinition.
  3. Create compartment node providers for the three state action compartments: STVEntryCompartmentNodeDescriptionProvider, STVDoCompartmentNodeDescriptionProvider, STVExitCompartmentNodeDescriptionProvider. Each shows StateSubactionMembership-owned actions.
  4. (Optional) Add pseudostate nodes using a custom SVG image style — look at how the Package node renders its icon for the SVG pattern.

Phase 3 — Create edge providers

  1. Create TransitionUsageEdgeDescriptionProvider extending AbstractEdgeDescriptionProvider. Source and target are both StateUsageNodeDescription.
  2. Add label support for guard/trigger/effect by implementing a getEdgeLabelExpression() override that calls an AQL service: "aql:self.stv_getTransitionLabel()".
  3. Add the AQL service method in DiagramQueryAQLService (or create a new STVQueryAQLService if the STV module is large enough to warrant its own service). The method reads the TransitionUsage's guard/trigger/effect members and formats them as a string.

Phase 4 — Fill in the stub

  1. Open StateTransitionViewDiagramDescriptionProvider.java. Replace the empty newDiagramDescription() call with a call to your STVDescriptionBuilder, passing the node and edge providers. Remove the stub comment about "only useful for the menu entry."
  2. Add a canCreateDiagram() precondition in StateTransitionViewCreateService (or equivalent) that restricts creation to StateDefinition context elements.

Phase 5 — Test

  1. Create a test class in backend/views/syson-diagram-tests/. Use the existing AbstractChecker subclasses — NodeDescriptionHasDirectEditToolChecker, NodeDescriptionHasDeleteToolChecker, EdgeDescriptionHasReconnectToolChecker — to validate all providers.
  2. Run: mvn -pl backend/views/syson-standard-diagrams-view -am test to verify the new providers pass all checker invariants.
  3. Start the application (UserTools/StartSysOn.bat or docker-compose up), open SysON at http://localhost:8080, create a project, open a model with a StateDefinition, and right-click → New Representation → State Transition View. The diagram should render with state nodes and transition arrows.
